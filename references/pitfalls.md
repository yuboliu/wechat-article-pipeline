# 踩坑记录（实测）

## 1. 中文引号归一化：别用「正则配对 + 循环」

微信公众号抓取结果里，中文左引号常被输出成右引号 `”`，甚至同一篇里左右混用。

**错误做法**：`text = re.sub(r'”([^”\n]{1,90})”', r'“\1”', text)` 并循环到收敛。

后果：第一轮把成对的 `”A”` 修成 `“A”` 之后，文本里剩下的是「右引号开头、下一个右引号结尾」
的孤例。第二轮正则会把跨句的两段文字当成一对强行配对，把不该改的右引号改成左引号。

实例（真实事故）：

```
原文：…让大模型”看整个页面 + 生成点击指令”，慢且贵。…从几个候选里”选一个”，…
一轮后：…大模型“看整个页面 + 生成点击指令”，慢且贵。…从几个候选里“选一个”，…   ✅
二轮后：…大模型“看整个页面 + 生成点击指令“，慢且贵。…从几个候选里“选一个”，…   ✗
```

**正确做法**：中文引号在**一行之内必然成对**，所以按行扫描，遇到引号就按出现顺序交替赋值。

```python
QUOTES = "“”"
def normalize_quotes(line):
    out, toggle = [], 0
    for ch in line:
        if ch in QUOTES:
            out.append("“" if toggle == 0 else "”")
            toggle ^= 1
        else:
            out.append(ch)
    return "".join(out)
```

跳过 ``` 围栏内的行（代码里的引号不能动）。此法对「左引号被写成右引号」「左右混用」
「一行多组成对引号」三种情况都成立。

## 2. 提取 tags：正则要容忍最后一行没有换行符

`re.search(r'^tags:\n((?:- .+\n)+)', fm_raw, re.MULTILINE)` 在 frontmatter 被
`^---\n(.*?)\n---\n` 切出来后，**最后一行不带 `\n`**（切割点把换行吃掉了），于是最后一个 tag
被静默丢掉。

写成 `((?:- .+$\n?)+)` 即可。这个 bug 不报错、只少一个标签，很容易漏掉 —— 落库后务必
确认 tag 数量与预期一致。

## 3. frontmatter 与 H1 之间会多出空行

拼接时若 `fm` 模板已以 `\n` 结尾，又写成 `"%s\n# %s"`，就会在 `---` 和 `# 标题` 之间插一个
多余空行。用 `"%s# %s"` 让 fm 自己的结尾换行承载分隔。

## 4. 图片嵌入必须独占一行

抓取结果常出现 `扫码访问官网👇![](images/img_003.png)` 这种图接在段落末尾。转换时统一替换为
`\n![[images/x.png]]\n`，再靠「3 个以上连续空行收敛为 1 个空行」把多余空行压掉。

## 5. 落库只复制被引用的图片

`output/<目录>/images/` 里通常混着封面图、二维码、活动海报、点赞引导图。这些的引用段落已在
转换阶段被删掉，所以落库时按正文里的 `![[images/xxx]]` 逐个复制即可，不要整目录 copy。
校验脚本会提示「文件多于引用」，那是正常的，不扣分。

## 6. 调用 Windows python 时的路径形式

Git Bash 下给 Windows python 传路径要用 `C:/Users/...`，不要用 `/c/Users/...`（会被歪曲成
`C:\c\Users\...`）。

## 7. 发布日期从哪来

`wechat_to_md.py` 抓出的 frontmatter `date` 常为空。可以从原文 HTML 里的
`var ct = "<10 位时间戳>"` 还原：

```python
m = re.search(r'var ct = "(\d+)"', html)
pubdate = datetime.datetime.fromtimestamp(int(m.group(1))).strftime("%Y-%m-%d")
```

拿不准时把日期留空，好过写错。

已实测：`var ct` 与原文页面上显示的发布时间（精确到分钟）一致，可信。

## 8. 微信会限流，别连着抓

同一篇文章短时间内重复 `requests.get` 会撞 `SSLError: UNEXPECTED_EOF_WHILE_READING`。
抓取脚本本身只请求一次，正常流程不会触发；但如果为了补日期 / 做 Tier-2 对照又去拉一遍，
中间夹一次 WebFetch 或隔一会儿再试即可，不要写重试循环硬刚。

## 9. Tier-2 对照的性价比比想象中高

Tier-1 只能证明「结构完整」，证明不了「内容没漏」。做一次 WebFetch 拉原文逐段对照，成本
只有一次请求，却能同时拿到三样东西：

1. **零遗漏确认** —— 把原文段落按序列出，与成品逐段打勾。2000~5000 字的公众号短文很快能对完。
2. **引号修正的验证** —— 原文里 `”` 和 `“` 的混用现场一目了然，能确认归一化方向对不对。
3. **发布时间的独立佐证** —— WebFetch 常能直接读到「2026年9月23日 07:10」这类时间戳，
   与第 7 条的 `var ct` 互为印证。

所以只要文章不长，别省这一步。

## 10. 图片链接可能带 title 属性（静默失效级）

微信偶尔在图片 URL 后附一个 title，值是 `undefined`：

```
![](images/img_000.png "undefined")
```

若正则写成 `\(images/([^)]+)\)`，捕获组会把 ` "undefined"` 一起吞进去，得到不存在的文件名
`img_000.png "undefined"` —— 不报错、图挂了。必须写成：

```python
r'!\[[^\]]*\]\(images/([^)\s]+)(?:\s+"[^"]*")?\)'
```

另外 alt 文本有两种形态：空 alt（`![](...)`）和 `![图片](...)`，用 `[^\]]*` 一并覆盖。

## 11. 反斜杠转义残留

| 形态 | 处理 |
|------|------|
| 独占一行的 `\` | 删行 |
| `change\_cert` | 还原为 `change_cert` |
| `\**加粗\**` | 还原为 `**加粗**` |

**不要无脑 `re.sub(r'\\', '', text)`** —— 会把 `C:\Users` 这类合法路径一起毁掉。
只在「反斜杠 + 标点/下划线」时还原：`re.sub(r'\\([_*\[\]()#!`>+\-.])', r'\1', text)`。

## 12. 加粗标记会被微信按 token 切开

原始 HTML 里一段连续加粗若被拆成多个 `<strong>`，转出来就是：

```
**3.****公告意外：7****月30****日发布**
```

合并方式：去掉**行内**连续的 4 个星号，即 `(?<=\S)\*\*\*\*(?=\S)` → 空串。
`(?<=\S)...(?=\S)` 边界不能省，否则会误伤独占一行的 `****`（Markdown 水平分割线）。

执行顺序：这条要在 **PART 标记清理之后**跑。

## 13. 机构文的 PART 标记与章节编号

券商/机构报告常见结构：

- `**PART**01**` / `**PART****02**` / `**PART02**` → 整块删除（章号已体现为标题）。
  正则 `\*\*PART\*{0,4}\s*\d+\*{0,4}[ \t]*\n?`。
- `**01**` 独占一行 + 下一行 `**章节名**` → 合并为 `## 01 章节名`。
- `**风险提示：**xxx` → `> [!warning] 风险提示` callout。
- 文首 `**文：xxx**` + `联系人：xxx` 若与顶部 info callout 重复，删除。

标题层级还可能遇到下面这些（因文章而异，按需取用，**先长后短替换**）：

| 原文形态 | 目标 |
|---|---|
| `- 1.1.1 标题` | `#### 1.1.1 标题` |
| `- 1.1 标题` | `### 1.1 标题` |
| `#### **引言**` | `## 引言` |
| `## **1、小节名**` | `### 1、小节名` |
| `## **无编号加粗段**` | `**无编号加粗段**`（还原为段落） |

⚠️ 先替换 `x.y.z` 再替换 `x.y`，否则 `### 1.1 xxx` 会把 `1.1.1` 的前缀吃掉。

## 14. 空引用行直接删

`^>[ \t]*$`（微信留下的空 blockquote 壳）没有任何信息，删掉。

## 15. 封面图堆叠

有的文章首图区是 3~4 张连图（`img_000`~`img_003`）加一段标题文字，属于公众号封面模板，
正文不需要。判断方法：这几张图紧挨在 H1 附近且彼此内容相似，删到只剩第一张或全删。

## 16. vault 根 = 含 `.obsidian` 的目录，本机路径只留一个「本机配置」

落库脚本的 `--vault` 要传 **vault 根**，不是笔记所在的分类目录。

- 默认解析顺序：环境变量 `WECHAT_VAULT` → `scripts/local_config.py` → `~/iNote`。
- ⚠️ 2026-09-23 用户重构过目录：原先 iNote 下还多一层 `知识库`（即 `iNote\知识库\公众号\...`），
  该层**已取消**，现在是 `iNote\公众号\...`。
- ⚠️ **2026-11-04 起本条的两处已过时**（保留原样是因为后面几条都引用了它）：
  1. 解析改由 `scripts/env_config.py` 统一负责，顺序是
     「命令行 → 环境变量 → 仓库根 `.env` → 报错」，**不再回落到 `~/iNote`** ——
     一个看着能跑、实则写错目录的默认值，比直接报错更难发现（见 #62）。
  2. `iNote` 这个目录已经不存在了（本机实际路径见 `.env`，不入库）。同一次整理里
     `公众号` 也被加上了编号前缀 —— 所以落库目录必须走通配解析，不能写死名字。

这类路径变更的隐蔽之处：**改了不会报错**。脚本会老实地在（新建的）旧路径下写出一份笔记，
Obsidian 里却看不到 —— 你会以为同步失败，实际是写到了别处。

所以本机路径只保留**一处权威来源**：`scripts/local_config.py` 里的 `DEFAULT_VAULT`
（该文件已在 `.gitignore` 中）。命令行一律走默认值，**不要**把它复制进 SKILL.md 的示例命令、
记忆文件或临时脚本里，更**不要写回 `sync_to_vault.py`** —— 那会让 `git pull` 次次冲突，
`git push` 还会把你的本机绝对路径公开出去。脚本已加两道保险：
`--vault` 不存在直接 `SystemExit`；存在但其下没有 `.obsidian` 时打 WARN（不拦，兼容非标准 vault）。

## 17. 落库后必须归一化换行符（CRLF 污染）

Windows 下用文本模式写文件（`Path.write_text()` / `open(..., 'w')`）会把 `\n` 翻成 `\r\n`；
而 vault 里既有笔记全是 LF。结果同一批笔记出现两种换行符 —— Obsidian 照常渲染不报错，
但 diff / 版本对比时会整篇标红。

2026-09-23 起 `sync_to_vault.py` 的内联 `create_note()` 已显式用 `open(..., newline="\n")`，
**不会**再产出 CRLF；脚本末尾那句 `\r\n → \n` 归一化保留为保底。如果你另外写脚本落库，
记得自己处理这一步。

顺带一个连带效应：`create_note()` 用**当时时间**重写 frontmatter 的 `created`。所以「重跑落库
应逐字节一致」的回归，要把 `created` 那一行排除后再比。

## 18. BASE 默认值曾指向死路径（静默重建）

到 2026-09-23，`to_obsidian.py` / `sync_to_vault.py` 的 `DEFAULT_BASE` 仍写死为
`~\WorkBuddy\微信公总号知识库\output` —— 该目录**当日已不存在**（整个
`微信公总号知识库` 不见了）。不传 `--base` 时脚本不会报错，而是用 `mkdir(parents=True)`
把这个死路径**重新建出来**，笔记写进去后 vault 里自然看不到，排查时极易误判为「同步失败」。

处理：两个脚本的 `DEFAULT_BASE` 已改为 `cwd/output`（与抓取器 `DEFAULT_OUTPUT_DIR` 一致），
命令行仍可用 `--base` 覆盖。**BASE 与 VAULT 都不要复制进文档或临时脚本**：`BASE` 跟随
cwd 即可，`VAULT` 放 `scripts/local_config.py`（见第 16 条）。

## 19. 章节标题是样式块，不是 `<h1-6>`

微信很多深度长文的章节标题写成：

```html
<section style="font-size: 17px;font-weight: bold;color: #ff6600;text-align: center">
  <span leaf="">AI推理流量四大核心特征</span></section>
```

markdownify 不认 `<section>` 的样式，会把它压成一行普通段落 —— 结果落库笔记**整篇没有 `##`**，
与 vault 里既有笔记（都是 `## 小节名`）风格不一致，阅读理解层次也丢了。

处理：抓取器 `process_content()` 已加确定性提升规则（见该文件 `# 2) 小标题` 注释）：
内联样式含 `font-weight: bold` 且 `font-size >= 16px`（正文 15px）、纯文本、≤40 字、
不以 `。！？；：` 收尾 → 提升为 `<h2>`。L1(17px 橙) 与 L2(16px 蓝) 统一压成一级 `##`，
与「H1 + 单层 ##」的既定风格一致。

改这条规则前先跑一篇有嵌套小标题的文章回归，确认没把正文里的强调块误判成标题（长度与
句末标点两道闸就是防这个）。

## 20. 标题里的 `|` 会让落库在 Windows 上直接崩

微信标题常带 ASCII `|`，例：「F5 数字图书馆 | DNS over HTTPS (DOH)架构」。
落库脚本原先**只对文件名**做了一次非法字符清理，而 **folder 是用原始 title 拼的**，
于是 `mkdir()` 抛：

```
OSError: [WinError 123] 文件名、目录名或卷标语法不正确。:
  ...\公众号\F5 数字图书馆 | DNS over HTTPS (DOH)架构
```

`| : ? * " < > \ /` 在 Windows 文件名里都非法（注意是全角 `｜` U+FF5C 才是合法的，
中文排版里两种都会出现，肉眼几乎分不清）。

修法：新增 `safe_name()`，规则与抓取器 `wechat_article_to_markdown.py` **完全一致**
（`[/\\?%*:|"<>]` → `_`、截断 80 字符、去掉结尾的点与空格），**folder 与文件名都走它**；
H1 正文保留原样（那是笔记内容）。副产品是 vault 里的文件夹名与 `output/` 目录名相同，
两处可互相追溯。

> 为什么之前 12 篇没暴露：标题里要么不含这些字符，要么用的是全角 `｜`。
> 落库前若看到标题含 `| : ? * " < >`，就知道要走 `safe_name()`。

## 21. 没有结尾 `---` 的文章，推广尾巴要靠文末标记截断

`find_promo_sep()` 只认 `---` 分隔线。但相当一部分文章**全文只有一条 `---`**
（紧跟元信息块那条），文末直接接「关注公众号 + 二维码 + 推荐阅读链接列表」，
没有结尾分隔线 —— 于是推广块整段留下，其中的推广链接还会被提成 `#` 标题、污染大纲。

例：「F5 数字图书馆 | DNS over HTTPS (DOH)架构」文末 90 行是
`**关注 F5社区 微信公众号**` + 二维码 + 「DNS 安全 / F5 Citrix / BIG-IP Next」三组
共 10 条 `mp.weixin` 推荐链接。

新增 `find_promo_tail()`，**仅在 `find_promo_sep()` 返回 -1 时**启用，两道闸：

1. 命中 `PROMO_TAIL_RE`（`关注…公众号` / `扫描…二维码` / `推荐阅读|近期好文|…` /
   `添加…微信` / 独立行 `end`）的行，且**从它到文末 ≤ 全文 33%**；
2. 尾巴里确有推广特征：≥1 条 `mp.weixin` 推荐链接，或 ≥2 个推广标记行。

> ⚠️ **第 1 道的比例闸不能省**：白皮书类文章常在**开头**放「扫描下方二维码」
> （本篇第 16 行「扫码获取白皮书」，尾巴占比 96%）—— 只认文字标记会把整篇腰斩。
> ⚠️ **回归**：重跑「思科2026报告深度解读」确认**逐行零差异**（该篇 0 命中）。
> 实测本篇：截断 2196 字符，230 → 155 行，校验②的「标题-正文粘连」WARN 变 PASS。

## 22. 文章**开头**的引流块，靠「连续同质行」截断

第 21 条处理的是文末。但白皮书连载类文章（如 F5「数字图书馆」系列）在**正文最前面**
先放一段引流：

```
![](https://mmbiz.qpic.cn/…/640?wx_fmt=png…)      ← 扫码图（远程，未本地化）
本章节节选自《企业 DNS 建设白皮书》。
**扫描下方二维码**
**添加 F5 市场部助手小安**
**即可免费获取完整白皮书**
**《企业 DNS 建设白皮书》**
![](https://mmbiz.qpic.cn/…/640?wx_fmt=png…)      ← 二维码（远程，未本地化）
```

两个后果：正文被这 16 行挡住；其中两张图抓取器**没本地化**，成品留 2 条
「残留远程资源」WARN。

新增 `find_promo_head()`，判定逻辑与文末不同 —— 它找的是「**从文首第一个引流行/远程图行起，
连续的同质行**」（空行、水平分割线 `---`、引流行、远程图都算同质），一碰到正文行
（本地图 `![](images/…)`、标题、长文本）立刻停，所以**不会跨进正文去砍**。

三道闸，缺一不可：

1. 块起点必须在全文**前 25%** 以内；
2. 块内 **≥2 个**引流标记行（单个标记不算，防正文里偶然一行「扫描二维码」）；
3. 块内必须有**索取诉求**（`获取|领取|下载|申请|加群|进群|私信|联系`）
   —— 只有一句「节选自《X》」不砍。

> ⚠️ **文首的 `---` 是透明的**：形态 B 的产物在正文最前面就有一条元信息分隔线
> `---`，第一次实现时它把「文首第一个非空行」占住了，导致整块识别不出来（返回 -1）
> —— 所以扫描时把 `---`/`***`/`___` 与空行同等对待。
> ⚠️ **回归**：重跑「思科2026报告深度解读」确认 0 命中（该篇文首是正文）。
> 实测本篇：截断 444 字符（16 行），成品首屏直接是 `![[images/img_003.png]]` +
> `**需求分析**`；校验的两条 WARN（残留远程资源、标题-正文粘连）双双转 PASS。

## 23. 转载社区的页脚：标记词不在「关注/扫码」里，一条都不命中

「容器云平台网络架构」（twt企业IT社区）文末整段推广**一个标记都没命中**，全部留下：


## 24. 章节标题没有层级：原来的实现会把 `###` 一律压成 `##`

「容器云平台网络架构」的成品**一个 `##` 都没有**，`**1 容器平台网络模型**`、
`**1.1 容器网络概述**`、`**1.2.1 协议栈**` 全是加粗文本 —— 大纲面板里什么都没有。

原因有两层：

1. **抓取层**：这类小标题是 `<p><span style="color:…"><strong><span style="font-size: 15px">1.2.1 协议栈</span></strong></span></p>`
   —— 加粗在**内层** strong/span 上、字号 14~15px、外层是 `<p>`；而抓取器只认
   带样式的 `<section>`，规则空转（已在 `wechat-article-to-markdown` 加 `2b)` 规则修掉）。
2. **格式化层**：本 skill 原来只有一句
   `text = re.sub(r"^###\s+", "## ", text)` —— **一律压成一级**，即便上游给了层级也保不住。

修法：新增 `rebuild_headings()`，**按标题里的编号**定级，替换掉那句压平：

| 形态 | 层级 | 例子 |
|---|---|---|
| `1 xxx` | `##` | `1 容器平台网络模型` |
| `1.1 xxx` | `###` | `1.1 容器网络概述` |
| `1.2.1 xxx` | `####` | `1.2.1 协议栈`（封顶 6 级） |
| `01安全问题`（两位编号） | 上一级 + 1 | `### 01安全问题` |
| `Underlay网络`（无编号加粗，位于数字小节内） | 上一级 + 1 | `##### Underlay网络` |
| `## 总结`（抓取器定的无编号标题） | 保持原级 | 不动 |

「够不够格当标题」的闸（`bold_can_be_head()`）：≤40 字、不含 `。`、结尾不是句末标点
（`：` 拦住了 F5 篇的引导句「应重点考虑以下技术建议：」）、不以「图/表/注」开头（图注）。

> ⚠️ **「编号后必须有分隔符」不能省**：否则 `802.1Q标准` 会被 HEAD_DOT 匹配成
> 「编号 802.1 + 正文 Q标准」。现在要求编号后跟分隔符**或直接接汉字**。
> ⚠️ **回归**：「思科2026」重跑**逐字节零差异**（它的标题都是无编号 `##`，规则不碰）；
> 「F5 数字图书馆」重跑会把 `**需求分析**` 抬成 `##`、`**01安全问题**` 抬成 `###`
> —— 这是期望的改进，但**已落库的笔记不擅自重跑**，要改先问。
> 单测见 `tests/test_heading_levels.py`（形态、层级、反例共 8 项）。

## 25. 「目录」块被 markdownify 挤成一行

微信的目录是一串并列的 `<section>`，而 markdownify 不认识 `<section>`，把整份目录
**连成同一行**、加粗标记也退化：

```
**目录**
**1 容器平台网络模型**1.1 容器网络概述1.2 容器网络分类介绍1.2.1 协议栈…4.2.3 Calico
```

这一行在 Obsidian 里占满屏宽、没法读，且完全没有结构。新增 `rebuild_toc()`：
把条目按编号重排成**嵌套列表**（`- 1 …` / `  - 1.1 …` / `    - 1.2.1 …`）。

四条闸全中才动（「一行里塞满编号」也可能是正常正文）：

1. 上一行（允许隔空行）是「目录」标题；
2. 该行 ≥ 100 字；
3. 编号起点 ≥ 4 个，且**行首就是编号**；
4. 每段都能解析成「编号 + 文字」，否则整块不碰（宁可不动，不能改错）。

> ⚠️ **必须用 `finditer` 定位条目起点，不能用 `re.split`**：零宽前瞻的 `split` 会在
> 匹配点后跳过一个字符，于是 `1.1 容器网络概述` 被二次切成 `1.` + `1 容器网络概述`
> —— 第一版就是这个 bug，切出 42 段（正确是 20 段）。
> ⚠️ 已知局限：条目文字里若含「数字 + 空格」（如 `支持 IPv6 双栈`）会多切一段。
> 目前遇到的目录都没这种写法；真遇到只是列表多一项，不丢内容。


## 26. 「大节标题」在 HTML 里和小节字号**完全相同**，只能靠「后面有没有正文」判断

「基于基础网络的SDN组网原理分析」的排版：

```
**SDN VBC控制平面**          ← 大节，后面一个字都不写
**GoBGP消息同步机制**         ← 子节
**0****1****GoBGP speaker和RS-Node**   ← 小节（编号）
```

三行的 HTML 都是 `<section style="font-size:16px"><strong>…`，**同样的字号、同样的加粗、
都没有编号** —— 靠样式完全分不出层级。`rebuild_headings()` 只能按「无编号 → 顶层」处理，
于是 `SDN VBC控制平面` 和 `GoBGP消息同步机制` 双双变成 `##`，大节退化成一个空标题。

新增 `fold_empty_heads()`。**判据只有一条**：标题 A 与紧随其后的标题 B 之间
**没有任何正文行**（空行、图片、图注、`---` 都不算正文）→ A 是「章标题」，
B 及其同级兄弟整体降一级。作用域在两种情况下关闭：

1. 遇到比 A 更浅的标题；
2. 遇到一个「自己就要开编号子节组」的无编号标题（它后面紧跟 `01` 这类两位编号）
   —— 那是新的一章，不该继续吃上一章的缩进。

本篇效果：`## SDN VBC控制平面` 保留，其下 `GoBGP消息同步机制` / `BGP EVPN消息` /
`BGP IPv4路由消息` 降为 `###`，三条同步链路降为 `####`；而 `SDN VBC 数据平面`
（条件 2 命中，它后面紧跟 `01同VxNet…`）正确留在 `##`，没有被误吃进上一章。

> ⚠️ **回归**：拿全部已落库成品重跑，除「本就该被上一批规则改善」的那篇外**零变化**。

## 29. 「加粗小标题」被微信切碎的四种形态（含 `1.` 小节与 num_depth 的联动）

同一篇文章里小标题可能以四种形态出现（G行那篇四种全有）：

| 形态 | 原始 | 应变成 |
|---|---|---|
| 编号被切开 | `**0****1****动静区分**` | `**01 动静区分**` |
| 章标题与小节标题同行 | `**策略设计****01****智能解析机制**` | `**策略设计**` + `**01 智能解析机制**` |
| 小节标题与正文同行 | `**03****域名解析时延**域名解析作为…` | `**03 域名解析时延**` + 正文 |
| 编号行与标题行分开 | `**02**` ⏎⏎ `**域名规划**` | `## 域名规划` |

前三者由 `normalize_bold_headings()` 处理，**必须跑在通用的「加粗分裂合并」
（`**A****B**` → `**AB**`）之前** —— 那一步会把结构边界抹平，之后就再也分不出来。

第四种是 convert() 里的两行合并正则：它早年要求「编号行与标题行**紧邻**」，而微信常在
中间夹一个空行，于是整篇漏掉 —— 已改成允许空行。**合并后把编号丢掉**
（出 `## 域名规划` 而不是 `## 02 域名规划`）：两位编号在 `rebuild_headings()` 里被归为
「小节」（`two`），留着会把章标题一起压成 `###`。

拆分门控（`SPLIT_HEAD_RE`）刻意**不含** `1 标题`（无点）—— 「容器云」的目录行
`**1 容器平台网络模型**1.1 …` 正是那个形态，拆了就把目录拆坏。

### 连带改动 1：`1.` 小节的层级

「F5」那篇的小节写作 `**1. SSL 卸载。**实现…`（编号带点，且标题那句的句号被包进加粗里）。
`HEAD_DOT1_RE` 把 `1. 小节名` 定为层级 3（「点号数 + 2」），并剥掉加粗块末尾的 `。`。

⚠️ 但 `kind == "dot1"` **不能更新 `num_depth`**。`num_depth` 的作用是让无编号子标题挂到
更深一级（容器云的 `1.2.1 协议栈` 下面的 `Underlay网络`）；而 `1.` 级小节的兄弟往往就是
**无编号的章标题** —— F5 的 `1.–7.` 后面紧跟 `架构分析`／`技术建议`，一旦 dot1 抬高
num_depth，这两个章标题会被误压到 `####`（vault 里已有的 F5 成品是 `## 架构分析`）。

### 连带改动 2：空章折叠遇到带编号小节时不折

`fold_empty_heads()` 原来的作用域只在「遇到更浅的标题」时关闭，于是**同级**的 `## 总结`
会被一直吞在作用域里、跟着被降一级。现在加一条：空章标题后面紧跟的是**带编号**小节
（`01 …`）时不启动折叠 —— 层级已由编号定好，再折就是多降一级。

### 回归

- `tests/test_bold_headings.py`（14 项，纯标准库）；
- 全部已落库成品重跑：容器云 / 思科**逐字节零变化**；F5 重跑后 18 个标题与 vault 版
  **逐行一致**；SDN 只多了编号后的空格（`#### 01 GoBGP speaker和RS-Node`）。

## 30. 作者把 Word 的 `<h1>`/`<h2>` 直接粘进正文，整套层级深一级

「云原生应用可观测架构设计」（twt企业IT社区）那篇的正文长这样 —— 作者是从文档里
粘过来的，所以 HTML 里是**货真价实**的标题标签：

```html
<h1 ...><span style="font-size: 17px;color:#007aaa;font-weight: bold;">一、引言</span></h1>
<h2 ...><span style="font-size: 15px;color:#007aaa;font-weight: bold;">2.1 全栈覆盖：分层观测模型</span></h2>
```

markdownify 原样给出 `#` / `##`。而本脚本的约定是「H1 只属于文章标题、`##` 是顶层章」
（抓取器的字号规则把 `<section>` 推成 `<h2>` 正是这个口径）—— 两套约定一撞，结果是：

- 正文章节与文章标题**同级**（`# 一、引言`，一个笔记里冒出 6 个 H1）；
- `rebuild_headings()` 里「H1 一律不动」的分支让它们纹丝不动；
- 小节 `## 2.1 …` 反而比它的章深一级，整个大纲塌掉。

**判据：正文里还存在 H1 就认定是这种文章。**（脚本自己的标题 H1 已被 `read_quote_meta`
摘掉；文末推广里的 `#` 链接也在截断时去掉了 —— 已对全部已落库成品回归验证。）
命中后 `shift_body_headings()` 把正文**所有标题深度 +1**（封顶 6）。

两点设计决定：

- **编号标题其实不受影响** —— 它们的绝对层级由 `rebuild_headings()` 按编号重算，
  `2.1` 照旧是 `###`。真正靠这一步纠正的是**无编号**标题：`一、引言` → `##`，
  `## 实践一：…` → `###`。
- 与文章标题**同名**的 H1 行按「重复标题 banner」丢弃（`strip_dup_title_head()`
  只认加粗形态，认不出 H1），并且**不算**「存在正文 H1」的证据 —— 否则会把一篇
  正常的文章整体下移一级。

回归：`tests/test_word_headings.py`（8 项）；5 篇成品重跑**零影响**。

## 31. `**3.可视化展示**`：加粗的编号**列表项**被误当成小标题

同一篇里，`解决思路：` 下面是 `1.数据捕获与处理` / `2.埋点流程设计` / `**3.可视化展示**`
三个并列列表项 —— 作者只给第 3 项加了粗，于是它独占一行、通过 `bold_can_be_head()`，
被 `HEAD_INT_RE` 判成 `int`（顶级章）→ 大纲里冒出 `## 3.可视化展示`，
夹在 `### 实践一：…` 和 `### 实践二：…` 之间。

**规则：加粗行若形如「编号 + 点号 + 紧跟非空白」（`^\d+[.．](?!\d)\S`），是列表项，不是标题。**
依据是本项目已有的约定 —— 标题一律在点号后留空格（`1. SSL 卸载`，见 `HEAD_DOT1_RE`）；
而 `(?!\d)` 让多位编号（`1.2.1 协议栈`）继续走 `HEAD_DOT`，不受影响。

实测：这条形态在已落库的 5 篇里 **0 命中**；`tests/test_word_headings.py` 覆盖了
「列表项不提升 / `1.2.1` 仍提升 / `1. SSL` 仍提升」三种情形。

> 附带发现：`## 3.可视化展示` 是**改动前就存在**的老毛病（用 `git show HEAD:` 的旧脚本
> 跑同一篇复现过），不是新规则引入的 —— 排查这类问题时值得先做这个对照。

## 32. banner 尾巴上的 `***DeepSeek***`：一个假标题能压深半篇大纲

「浅谈G行大模型上云部署方案」的文首 banner 是三行：


前两行拼起来正好等于 H1，`strip_dup_title_head()` 认得；第三行是**粗 + 斜体**（三颗星），
`BOLD_RUNS_ALL_RE`（`^\*\*[^*\n]+\*\*$`）不认 → banner 在第二行就断，`***DeepSeek***` 留下，
再被 `BOLD_ONLY_RE` 吃掉外侧两颗星 → `## *DeepSeek*`。

**真正的坑是连带效应**：这个「无编号的 plain 假标题」后面只跟了三张装饰 GIF（图片不算正文），
`fold_empty_heads()` 于是认定它是「空章标题」，作用域一直开着 —— 后面的 `## 引言`、
`## 1 大模型上云技术挑战`、`## 2` 全被压成 `###`。**一个假标题毁掉半篇大纲。**

**规则**：banner 认出来之后，继续往后吃「空行 / 纯图行 / 分隔线 / 纯装饰强调行」。
装饰行只认**三颗星**（`^\*{3}([^*\n]+)\*{3}$`，且 ≤20 字、不带句末标点）——
放宽成两颗星会把首屏的 `**引言**` 一起删掉（它是货真价实的正文小标题）。

回归：`tests/test_chapter_numbering.py::TestBannerDeco`。

## 33. 「一位数章号」体系：同一套 `**NN**` + `**名称**` 语法，两种口径

`**01**` + 下一行 `**架构设计**` 在「G行 DNS」那篇是**章**（→ `## 架构设计`，编号丢掉）；
在「浅谈G行大模型上云部署方案」里 `**03**` + `**AI算力硬件感知调度：…**` 却是**节**
（→ `### 03 AI算力硬件感知调度：…`，编号保留）。语法一模一样，区别全在**编号的位数体系**：

* 有**一位数章号**（`**1**`/`**2**`/`**3**`/`**4**`）→ 两位数是「跟着上一级」的节 → `### NN 名称`；
* 全文没有一位数章号 → 两位数自己就是章（「G行 DNS」）→ `## 名称`。

判定用 `SINGLE_CHAP_RE`（`^\*\*\s*[1-9](?:\*\*|\s*[^\d\s])`），**在「加粗分裂合并」之后**
取一次。⚠️ `01` 这类两位数**不会**误命中（`[1-9]` 挡掉了 `0`）—— 这正是「G行 DNS」
能保住原口径的原因。合并逻辑抽成了 `merge_numbered_names()` 以便单测。

同一篇里章号的三种写法也都要认：

| 原文形态 | 处理 |
|---|---|
| `**2**` + 空行 + `**大模型上云部署方案**` | `merge_numbered_names()` → `## 2 大模型上云部署方案` |
| `**3****大****模型上云成果**` | `_pair_number_title()` 把「编号在**开头**」的碎片拼回 → `**3 大模型上云成果**` |
| `**4**总结` / `**1******大模型上云技术挑战****` | `normalize_bold_headings()` 形态 4：章号在块内、标题在**块外**同行 → `**4 总结**`（块后残留的 `****` 一并剥掉） |

回归：`tests/test_chapter_numbering.py`；6 篇成品重跑**逐字节零差异**（含「G行 DNS」）。

## 34. `**END**![](images/img_013.gif)`：结束标记后面挂着图，`PROMO_TAIL_RE` 认不出来

正文结束处写 `**END**![](images/img_013.gif)` —— 图挂在同一行，而 `PROMO_TAIL_RE` 的 `end`
分支要求 `\s*\*{0,2}\s*$` 收尾，被图挡住 → 认不出。于是退到下一个标记（`**编辑：郜斌**`）
才截，**作者署名与简介留在了笔记里**（其占比 34%，而 33% 的比例闸又把更早的
`**作者：赵序光**` 挡掉了 —— 只差 1.1%）。

**规则**：新增 `find_promo_end()` —— `**END**` / `完` / `全文完` / `本文完`（可挂结尾装饰图），
比例闸放宽到 60%，另要求尾部有推广特征（mp 推荐链接，或 ≥2 个推广标记行）。

⚠️ **两个候选取更靠前的那个**（`min(find_promo_tail, find_promo_end)`），不能简单让 END 优先：

回归：`tests/test_chapter_numbering.py::TestFindPromoEnd`（含 F5 形态的 `t < e` 不变量）。


## 35. 作者把 Word 的 `<h3>`/`<h4>` 粘进正文（整篇偏深）+ 摘要被套了标题样式

样本：「不管你是运维还是开发，微服务这些你得知道!」（高效运维）。
HTML 里章节是**货真价实的 `<h3>`**（`font-size:1.3em; font-weight:bold`）、小节是 `<h4>`（1.2em），
markdownify 照实输出 `###` / `####` —— 于是**整篇比约定深一级**（`### 一、还是从网站开始`），
而抓取器的正口径是「`#` = 文章标题、`##` = 顶层章」，大纲整体矮一头。

同一篇里还有第二种：文首两条**摘要**也被套了 `<h3>`（外层 `text-align:justify`、内层
`font-size:15px`、**没有加粗**）：

```
<h3 style="text-align: justify;line-height:1.75em;margin-bottom:16px">
  <span style="font-size: 15px;color:#444">本文从一个网站为切入点，…优化举措。</span></h3>
```

→ `### 本文从一个网站为切入点，…优化举措。` —— 一条 78 字的段落变成假标题。**危害不止一条假标题**：
`fold_empty_heads()` 只看「两个标题之间有没有正文行」，假标题会把它后面的标题一起带歪。

**规则一：`shift_body_headings()` 从「有 H1 就整体 +1」改成「把正文最浅的一级归一到 `##`」**
（`shift = 2 - min(正文标题层级)`，结果夹在 2~6）。原来只处理偏浅的 `<h1>`/`<h2>`，
现在同一段代码也覆盖偏深的 `<h3>`/`<h4>`。与文章标题同名的 H1 行仍按 banner 丢弃且**不计入**统计。

**规则二：`demote_fake_headings()`** —— 正文标题（`##` 及更深）若
「空 / 是 `图片`（markdownify 对「标题裹图」的产物）/ > 40 字 / 含 `。` / 以 `。！？；：` 收尾」，
降回普通段落。必须跑在 `shift_body_headings()` **之前**（层级归一要看最浅的一级，假标题会带偏）。
实测全量 8 篇语料**只命中这一篇的 2 行**，0 假阳性。

### 连带修正：`fold_empty_heads()` 的折叠量改成**差值**

折叠量原本是无条件 `+1`。这在「SDN」那篇是对的 —— `## SDN VBC控制平面` 的子节们全塌到了 `##`，
整组 +1（含其后代 `01/02/03`）才对；但本篇 `## 四、总结` + `### 何谓微服务`（`###` 来自 Word 的
`<h4>`）本来就恰深一级，再 +1 就跳级成 `####`（`##` 直跳 `####`）。
改成 `delta = max(0, (scope + 1) - 第一个子节的层级)`，差值一致地传给整个作用域。
⚠️ 中间试过「只保证 ≥ scope+1」（`max(level, scope+1)`）—— **把 SDN 的 `#### 01 …` 拉成了 `###`**，
因为后代是靠差值链起来的，不是各自独立判断的。这个回归是跑全量成品才发现的。

### 抓取器侧（同批修掉）：标题标签里裹着图片 ⇒ **图片整条丢失**

```
<h3 style="text-align:center"><span><img data-src="…/640?wx_fmt=gif" alt="图片" /></span></h3>
```

markdownify 的 `<hN>` 转换只保留 alt 文字 → 渲染成 `### 图片`：**图没了**（`img_001.gif` 下载了
却从未被引用，成了孤儿图），还白送一个假标题。规则：`process_content()` 里把**含 `<img>` 的
`<hN>` 拆成 `<p>`**（图片不可能是标题内容），后续 markdownify 照常输出 `![alt](url)`。
回归：`tests/test_core.py::test_image_inside_heading_is_not_lost` 等 2 项。


## 36. 标题文字**整行被加粗**（`## **1. 引言**`）⇒ 编号认不出来，层级重建静默失效

作者在 Word 里把标题文字整体加粗，粘进公众号后 HTML 是「标题标签 + 内层
`font-weight:bold`（或 `<strong>`）」，markdownify 于是输出 **`## **1. 引言**`**。

**真正的代价不是样式**：`classify_head_number()` 拿到的是 `m.group(2).strip()`
（含 `**`），首字符是 `*` ⇒ `HEAD_DOT_RE` / `HEAD_DOT1_RE` / `HEAD_INT_RE` 全部不匹配
⇒ 一律判 `plain` ⇒ **整篇的编号层级重建（`1.` → `##`、`2.1.` → `###`）失效**，
只剩 `shift_body_headings()` 的整体平移。

这一篇里就露了马脚：所有章标题都是 `# **N. xxx**`（加粗），唯独
`## 3. 知识图谱技术`（**恰好没加粗**）能被 `classify_head_number` 认出来 ——
于是它被当作 `dot1` 定为 `###`，**比它的子节 `3.1.` 还深**，大纲塌了。

**修法**：新增 `unwrap_bold_head(txt)` —— 只有「整行恰好是一个加粗块」（`BOLD_ONLY_RE`）
才拆掉外层 `**`，半截加粗（`**重要**提示`）原样不动。在 `rebuild_headings()` 里：

* **第一遍扫描**（判 `has_multi_dot`，见 #37）也要用拆掉后的文本；
* 主循环里 `head = (unwrap_bold_head(raw), 层级, raw)`，`plain` 分支输出的仍是
  拆掉后的行（`txt != raw` 时重建该行），因此结果与其余笔记的标题风格一致。

**顺带修掉的同类问题**：**括号编号**的加粗行。`**（1）朴素 RAG- Native RAG 阶段**`
（`（1）`/`（2）`/`（3）` 并列在 `2.2` 下面）被提升成了 `##`，把 `2.3 存在不足`
挤成了「三个子的节」。`BOLD_LIST_ITEM_RE` 从「`\d+[.．]` 紧跟非空白」扩成
`^(?:\d+[.．](?!\d)\S|[（(]\d{1,2}[）)])` —— **括号编号从来不是本项目的标题编号**
（标题只用 `1` / `1.1` / `01` 三种），一律当列表项。

回归：`tests/test_word_headings.py::TestUnwrapBoldHead`（3 项）、
`::TestParenNumberedBoldItem`（3 项）。全量 9 篇既有成品**零影响**。

## 37. `1.` 到底是「章」还是「节」：看**全文有没有两级点号**

同一套「单级点号」写法，在两篇真实文章里含义相反：

| 文章 | 章 | 节 | 全文有无 `1.1` |
|---|---|---|---|
| 「F5 数字图书馆」 | `## 架构设计`（**无编号**，每章重新编号） | `1. SSL 卸载` → `###` | 无 |
| 「基于知识图谱增强RAG…」 | `1. 引言` / `2. RAG 知识库` | `2.1. 知识库概述` → `###`、`5.3.1.` → `####` | 有 |

2026-10-13 只见过前者，于是 `HEAD_DOT1_RE`（`1.` 开头的单级点号）被硬编码成层级 3。
本篇撞上后者 ⇒ `1. 引言` 与 `2.1. 知识库概述` **挤在同一级**，且 `## 3. …` 掉成 `###`。

**修法**：`classify_head_number(txt, multi_dot=False)`，`multi_dot=True` 时 `dot1` 返回层级 **2**。
`multi_dot` 由 `rebuild_headings()` **第一遍扫描**给出：

* 只扫「`#` 标题行 + 独占一行的加粗行」，用 `classify_head_number(...)[0] == "dot"` 判定；
  用 `unwrap_bold_head()` 先拆掉标题上的 `**`（否则第一遍也认不出来，见 #36）。
* ⚠️ **不能对全文扫 `\d+\.\d+`** —— 正文里 `802.1Q标准定义了 VLAN 标签…` 这行就会中招。
* `multi_dot=True` 时 `dot1` 与 `int` 同等对待（同步更新 `num_depth`）；
  `False` 时**保持原状**（层级 3、不抬 `num_depth`）—— F5 的口径一字未改。

「F5」那篇回归：`### 1. SSL 卸载` … `### 7. 功能灵活扩展` 全部原样，`## 架构分析` 也没被压。

回归：`tests/test_chapter_numbering.py::TestSingleDotNumberScope`（5 项）。

## 38. 转载社区的页脚**换了一版**：`原题：` 那行没了，其余行一条都命不中

twt 社区的页脚原先靠 `> 原题：…` 命中（pitfalls #23）。2026 版页脚把它换掉了：

```
> 支持社区支持本文同行观点，请点赞、转发或点击“♡”

> 欢迎点击文末阅读原文，可以直接看到社区中本文中可能不包括的的全部信息和最新更新

关联推荐：[A](mp链接)[B](mp链接)[C](mp链接)[D](mp链接)

欢迎关注社区**“大语言模型”相关**内容**，**了解最新行业同行专家的分享和大家的观点。

地址：https://www.talkwithtrend.com/Topic/154263

长按二维码关注公众号

![](images/img_006.jpeg)      ← 二维码

*本公众号所发布内容仅代表作者观点，不代表社区立场，封面图片由AI生成

点击下方↙↙↙阅读原文，更丰富，更精彩
```

`PROMO_TAIL_RE` 里**一条都对不上** —— 原因是两条通用缺陷，不只是「标记词没收录」：

1. **标记不在行首**：`> 欢迎**点击**文末**阅读原文**，…`、`…请**点赞、转发**…`。
   老写法把 `点击(?:阅读原文|在看)` / `欢迎关注[^\n]{0,24}` 都锚在（去 `>` 后的）**行首**，
   行首是「欢迎」「支持社区」就永远不匹配。
2. **标记后面还跟着一整句**：老写法普遍以 `\s*\*{0,2}\s*$` 收尾（要求标记基本到行尾）。

**修法**：新增一组**宽松写法**，各自带一个 ≤16 字的行内前缀 + `[^\n]*` 吃掉尾巴：

```python
r"|[^\n]{0,16}点击[^\n]{0,12}阅读原文[^\n]*"
r"|[^\n]{0,16}长按[^\n]{0,6}二维码[^\n]*"
r"|[^\n]{0,16}(?:关联|相关|往期|精彩)推荐\s*[:：][^\n]*"
r"|[^\n]{0,16}本公众号[^\n]{0,8}(?:发布|所发)内容[^\n]*"
r"|[^\n]{0,16}(?:请|欢迎)?点赞[、，,]\s*转发[^\n]*"
```

⚠️ **两道闸照旧不能松**：① 尾巴 ≤ 全文 33%；② 尾巴里要有 mp 链接或 ≥2 个标记行。
放宽后仍要能挡住「正文里偶然一句『点击下面阅读原文』」——
`tests/test_promo_trim.py::TestPromoTailCommunityFooterNoOrigin` 里专门有一条反向用例。

**副作用（是修好，不是误伤）**：「云原生可观测」那篇的页脚本来还有两行
（`> **有任何问题可点击“阅读原文”到社区原文下留言**` /
`> **觉得本文有用，请**转发、点赞或点击“♡”**…**`）没被截掉，现在一并截掉。
全量 9 篇里**只有这 1 篇**的产出变化，且是变好。

回归：`tests/test_promo_trim.py::TestPromoTailCommunityFooterNoOrigin`（3 项）。

## 39. 结尾「后台（对话框）私信…获取…白皮书」：`kill` 规则的三个并列条件差了俩

「MIT发布Agent信心指数」那篇结尾是一行引流语：

```
模智空间后台对话框私信260702获取完整白皮书！
```

`convert()` 里早有一条整行删除规则（`kill` 列表，2026-10-13 加的）：

```python
(r"^.*后台私信.*(?:获取|领取|下载).*(?:原文|报告|文件|资料|PDF).*$", "『后台私信获取原文』引导")
```

它要求**同时**满足三件事，这句恰好差两个：

| 条件 | 正则片段 | 本篇 |
|---|---|---|
| ① 「后台」与「私信」**紧邻** | `后台私信` | ❌ 中间夹着「对话框」 |
| ② 动词 | `获取\|领取\|下载` | ✅ `获取` |
| ③ 资料名词 | `原文\|报告\|文件\|资料\|PDF` | ❌ 结尾是「白皮书」 |

**改法**：`后台私信` → `后台[^\n]{0,6}私信`（容忍中间 ≤6 字的样式词），名词补
`白皮书|文档|全文`。三个条件仍要同时成立 —— 「后台…私信 + 动词 + 资料名词」
同现的正文正句基本不存在（已补反向用例）。

**为什么不去松 `PROMO_TAIL_RE` 那两道闸**：单行引流语**刻意**过不了那两道闸
（尾巴 ≤33%、尾巴里要有 mp 链接或 ≥2 个标记行）—— 白皮书类文章**开头**的
「扫描下方二维码」占比可达 96%，全靠比例闸挡着（pitfalls #21）。所以单行残留
走这条 `kill` 规则，千万别为了方便去动那两道闸。

回归：`tests/test_promo_trim.py::TestBackstageClaimLineKill`（3 项）；全量 11 篇
成品「旧 vs 新」**零差异**，只有本篇按预期少 27 字符。


## 40. 研报文末的「历史文章导航区」比正文还长 ⇒ 33% 比例闸必然拦下它

**样本**：「【华创策略姚佩】硅基产业链的消费映射——AI"新物种"的需求图谱」。

正文结束后是 `**再通胀牛市市场观点：**` + 200 来条自家文章链接（按主题分小节：
`**反内卷系列：**` / `**科技AI系列：**` / `**自由现金流系列：**` / `**十五五系列：**` …），
再往后是 5 段 `**法律声明**`、`![[images/img_034.gif]]`、「欢迎长按二维码关注」、
二维码图。整块 **36 k 字符**，而正文只有 47 k —— **占全文 33.9%**。

`find_promo_tail()` 的比例闸是 `尾巴 ≤ 33%`，**差 0.9 个百分点被挡掉**，
于是 200 多条链接连法律声明带二维码全留在了笔记里（产出 407 行 / 35 图，
正常应为 179 行 / 33 图）。

**根因不是「标记词不够」** —— `**再通胀牛市市场观点：**` 后面那些链接行里，
任何一条都不可能命中 `PROMO_TAIL_RE`（那是给「关注公众号 / 推荐阅读」这类
**文字标记**用的，导航区里根本没有这类句子）。比例闸又把它按死了。

**与 #21 的关系**：那条闸**不能拆**。白皮书类文章**开头**的「扫描下方二维码」
占比可达 96%，靠比例闸挡着才没把整篇腰斩。所以这里换一个**正交判据**：
不看「尾巴够不够小」，看「尾巴够不够纯净」。

**实现** `find_promo_nav()`：

1. 找**最后一行**满足「去掉 markdown 链接后残留 ≤8 字符」的行（即整行只由
   `[标题](url)` 组成，允许外层 `**`）；
2. 从它向上回溯，只吃三类行 —— 空行 / 短小节标题（`^\*{0,2}[^\n*]{2,20}\s*[:：]\*{0,2}$`）/
   链接行；撞到正文（长句、图片、署名）立刻停；
3. 整块含 **≥8 条** `mp.weixin.qq.com/s?` 链接才认定是导航区（3~5 条的
   「往期推荐」小列表交给 `find_promo_tail` 就够了，别抢它的活）。

`convert()` 里把它作为**第三个候选**与 `find_promo_tail` / `find_promo_end`
一起 `min()`（取更靠前者）—— 三者语义都是「推广区起点」，取更靠前的那个，
和 #34 的 F5 口径一致。

**为什么安全**：正文里不可能连续出现 8 行「整行只有链接」；`NAV_SECTION_RE`
单看很弱（正文里「风险提示：」同形），但它必须**紧邻 ≥8 条链接行**才计入，
而回溯遇正文即停，所以碰不到正文里的短标题。围栏感知照旧（代码块里的链接不算）。

**回归**：全量 12 篇成品「旧 vs 新」**11 篇零差异**，只有本篇按预期
`47404 → 11772`；单测
`tests/test_promo_trim.py::TestPromoNav`（5 项：正例 / 带系列小节+尾部二维码 /
链接不足 8 条 / 正文里的行内链接 / 代码围栏内链接）。

## 41. 同一号同一句措辞换一个字：`后台**回复**…获取…**综述**` ⇒ #39 的规则又漏了

**现象**：「79页RSI综述！」一篇结尾是单行

```
模智空间后台回复260923获取完整综述！
```

没被删。#39 那条 kill 规则要求三件事同时成立，这次差的正是其中两件：

| | #39 的写法 | 本篇 |
|---|---|---|
| 触发动词 | `后台[^\n]{0,10}私信` | 「后台**回复**」 ❌ |
| 结尾名词 | `原文/报告/文件/资料/PDF/白皮书/文档/全文` | 「完整**综述**」 ❌ |

**关键认识**：这是**同一规则的「同义替换」变体**，不是新形态 —— 和 #39 是同一个
公众号（模智空间）的两次再发版，一句是「后台**对话框私信**…获取…**白皮书**」，
一句是「后台**回复**…获取…**综述**」。这类句子的模板固定（`后台 + 动作 + 编码 +
获取 + 名词 + ！`），但措辞每次会换。

**改法**：不追着句子改，而是把两个「词位」都扩成集合，其余（三条件同时成立、
行首 `^.*` 锚定）不动：

```python
(后台[^\n]{0,10}(?:私信|对话框|留言|回复).*(?:获取|领取|下载).*
 (?:原文|报告|文件|资料|PDF|白皮书|文档|全文|综述|论文|PPT|课件|方案))
```

**为什么安全**：三个条件必须**同时**成立才删，且 `后台` 与动作词之间只允许 ≤10 字。
正文句子要同时凑齐「后台 + 动作」「获取/领取/下载」「公文名词」三样，几乎不可能
（已补反向用例：`系统支持在后台回复用户消息，管理员可随时查看记录。` 不被删）。

**刻意没动 `PROMO_TAIL_RE`**：这类句子是单行、过不了它的两道闸（尾巴 ≤33% /
要有 mp 链接或 ≥2 标记行），走 kill 列表就够了；而 #21 的「白皮书类文章开头
占比 96%」全靠那两道闸挡着，不能为一行引流语放松。

**回归**：全量 13 篇成品「旧 vs 新」**12 篇零差异**，只有本篇按预期 `9007 → 8980`；
单测 `tests/test_promo_trim.py::TestBackstageClaimLineKill`（+2 项，现 5 项）。





## 42. 文首 banner 的标题被**换行拆成两段** ⇒ 加粗认不出来，banner 整个留在首屏

**现象**：「浅谈网络安全纵深防御体系之自动封禁能力建设实践」一篇文首是

```
![](images/img_001.jpeg)![](images/img_002.png)…**浅谈网络安全纵深防御体系之

自动封禁能力建设实践**
```

banner 没删，四张题图 + 两行加粗标题全留在笔记首屏；那两行还会流进大纲。

**根因**：微信编辑器按断行切段，把**一对 `**` 拆到了两个段落**里。`_banner_bold()`
要求「整行恰好是一个加粗块」，前半 `**浅谈…之`（未闭合）与后半 `自动…实践**`
都不满足 → 返回 `None` → 循环以为遇到正文，直接 `break`。

**改法**：新增 `_banner_split_bold()` —— 本行是「`**` + 非星号文本」且没有收尾 `**`
时，向后最多跨 4 个非空行找「以 `**` 结尾」的那行，中间原样拼接。

**第二个坑（同一处，改完才暴露）**：旧逻辑是**一路收到底**再比对，只要 banner
后面紧跟别的加粗行（这篇正文第一行就是 `**引言**`），拼出来多一截、整体判定失败
→ 依然不删。改成**前缀式**：每收一块就比一次，**拼到恰好等于标题就 `break`**；
拼歪了（不再等于 `want` 的前缀）立刻 `return text` 一个字不动。

**回归**：13 篇既有成品零差异；`tests/convert/test_bold_headings.py` 新增 3 项
（跨行 banner / banner 后跟 `**引言**` / 无 banner 时正文首行加粗不动）。

## 43. 加粗标记粘连成 **4 颗、8 颗星号**（同一篇能出现三种形态）

**现象**：「浅谈自动封禁」一篇的列表项全是双份加粗：

```
- ****外部攻击告警量大，告警疲劳导致人工处置效率低下****      ← 首尾各 4 颗
- ****高效性****：针对海量告警数据实时分级分类…               ← 中间 4 颗
- ****精准性********：****自动封禁效率远超人工处置…           ← 8 颗 + 4 颗
```

渲染出来是一串裸露的 `*`，且把 `：` 后面整段拖成粗体。

**为什么 PART 清理也失效**：`****PART****03****` 同样粘连，旧 PART 正则从行首
`\*\*` 匹配不到 `PART`（中间还隔着两颗），只好放弃 → 剩一行光秃秃的 `**`。

**改法**：新增 `normalize_bold_runs()`，**只动两类行**（列表项、以 `****` 开头的行），
把 `\*{4,}` 一律折叠成 `**`；若该**列表项**剩下的 `**` 是奇数个，摘掉最后一个
（`**精准性**：**自动封禁…` 那个孤儿开标记后面本来就没闭合）。
**纯星号行（`***` / `****` 当 HR）必须跳过**，否则会留下一行光秃秃的星号。

**顺序**：必须**先于** PART 清理 —— 先归一成 `**PART**03**`，PART 正则才能整条吃掉；
反过来会残留一行 `**`。

**回归**：零差异；`TestNormalizeBoldRuns` 6 项（含 HR 与普通段落的反向用例）。

## 44. 标题行里残留 `**` ⇒ 编号被挡住、层级重建失效

**现象**：`## **1.事前策略预配置与仿真测试：**`、`## 自动封禁体系核心能力与落地实践**`
（后者是 #43 的粘连残留）。渲染时漏星号，且 `classify_head_number()` 看到首字符是
`*` 只能判 `plain`，整篇的层级重建失效。

**改法**：`fix_heading_lines()` 里对标题行做 `text.replace("**", "")`。标题本身
就有层级语义，`**` 在标题里只有坏处。

**顺带**：`bold_can_be_head()` 加一个例外 —— **带编号**且以冒号收尾的加粗行
（`**1.事前策略预配置与仿真测试：**`）算标题。原来「结尾 `：` 一律挡掉」是为了挡
引导句（`应重点考虑以下技术建议：`），但编号小标题带冒号是作者习惯。判据用
`classify_head_number()`，无编号的加粗句**仍按原规则挡掉**（已补反向用例）。

**还要过 `BOLD_LIST_ITEM_RE` 那一关**：`**1.xxx：**` 会被 ①「点号后紧跟非空白」
当成编号列表项而保留原级。所以该分支的条件改成
`BOLD_LIST_ITEM_RE.match(txt) and txt[-1] not in "：:"`。

## 45. 同篇 `## 1. 甲` 与 `## 2.乙` **混用** ⇒ 算出两个层级，大纲从中间塌掉

**现象**：「浅谈自动封禁」PART 02 的子节是 `###`，PART 03 的三个子节却是 `##`。

**根因**：`HEAD_DOT1_RE` 旧写法是 `^([1-9]\d*)\.\s+(\S.*)$` —— **点号后必须有空格**。
`1. 建设背景`（有空格）走 `dot1` → `###`；`1.高效性实践`（无空格）落到
`HEAD_INT_RE` 的 `int` → `##`。作者混用两种写法是常态。

**改法**：`\s+` → `(?!\d)\s*`。

- 空格去掉：两种写法等价。
- **`(?!\d)` 是必须的**：否则 `802.1Q标准` 会被读成「编号 802 + 标题 1Q标准」。
  单测 `test_numbering_kinds` 就是为它写的，这次一改立刻红了 —— 别删。
- `1.2.1 协议栈` 不受影响（`HEAD_DOT_RE` 先接走）。

**还有一处**：`rebuild_headings()` 对**标题行**也用了 `BOLD_LIST_ITEM_RE`，命中后
「保留原级」→ 与走 `dot1` 的兄弟撞成两级。改用 `HEAD_BRACKET_ITEM_RE`（只认
`（1）` 括号编号），`1.xxx` 形式的标题行正常走编号定级。

## 46. 中文序号 `四、…` 掉成一个普通段落 ⇒ 最后一章从大纲里消失

**现象**：「Gartner 发布 2027 十大战略技术趋势」：`## 一、` / `## 二、` / `## 三、`
都是标题，最后一节 `四、CIO与技术团队，该如何读懂这份报告？` 却是正文。

**根因**：抓取器只在原文是 `<hN>` 或带 `font-weight:bold` 的 `<section>` 时才给 `##`；
作者把这一节写成了普通段落。`classify_head_number()` 不认识中文数字，`rebuild_headings()`
也就无从提升。

**改法**：新增 `promote_cn_numbered_heads()`，**四道闸缺一不可**：

1. 全文已有 **≥2 个** `一、`~`十、` 形态的标题（说明这就是本文的章号体系）；
2. 候选行是独立短行（≤ 40 字），且不以 `。；，` 收尾（**`？`/`！` 放行** ——
   设问式标题很常见，这条正是本篇的形态）；
3. 该序号**还没有**同名标题（防目录项、重复段被提上来）；
4. 层级沿用既有中文序号标题里**出现最多的那一级**。

**回归**：13 篇零差异（其余文章没有中文序号体系，第 1 条闸就挡住了）。

## 47. 抓取器：`![](url "title")` 匹配不上 ⇒ 图**下载了**却仍指向远程地址

**现象**：「浅谈自动封禁」正文里的架构图在 Markdown 里是

```
![](https://mmbiz.qpic.cn/…/640?wx_fmt=png&from=appmsg "undefined")
```

校验报 `[WARN] 残留远程资源`。而 `images/` 里明明有 10 个文件、日志也写着
`✅ 10/10` —— **那张图已经下载成 `img_005.png` 了**，只是引用没被改写。

**根因**：`replace_image_urls()` 的正则是 `!\[([^\]]*)\]\(<url>\)`，**精确匹配
`![](url)`**。markdownify 对带 `title` 属性的 `<img>` 会输出 `![](url "undefined")`，
多一个 title 就整条不匹配。

**改法**：放宽成 `(?:\s+"[^"]*")?`。

**教训**：这类 bug 的伪装性很强 —— 下载数、文件数、校验的「图片数」三项**全都对**，
只有「残留远程资源」一条 WARN。**WARN 不要习惯性忽略**，它常常指向真问题。

## 48. 标题紧贴上一段正文（源码里没有空行）

**现象**：`rebuild_headings()` 提升出一行标题后，它可能紧跟在正文末行后面
（PART 清理把中间的空行一起吃了）。CommonMark 允许 ATX 标题打断段落，**渲染结果
是对的**，但源码里挤成一团，编辑时容易误合并。

**改法**：新增 `normalize_heading_layout()`：标题前若上一行非空就补一个空行；
顺带把 `### 1.xxx` 归一成 `### 1. xxx`（`(?!\d)` 保证 `1.2.1 协议栈` 不被拆坏）。

**这是本项目唯一一次「回归会命中已有成品」的改动**：13 篇里有 5 篇各多出 1~4 个空行
（纯版式，渲染完全不变，无内容差异）。**判定标准**：diff 里只有「新增空行」才算通过；
出现任何正文行的增删都说明改错了。

## 49. 表格「表头整行为空」（表头被写在 `<tbody>` 第一行）

**现象**：`图解从 IP 到 SRv6` 一篇的三层对照表，Markdown 是

```
|  |  |
| --- | --- |
| **层次** | **回答的问题** |
| 协议状态 | OSPF 邻居是否建立… |
```

Obsidian 把「层次 / 回答的问题」渲染成**第一条数据行**，表格看着少一行表头。

**根因**：公众号编辑器把表头写进了 `<tbody>` 第一行，`<thead>` 留空。
markdownify 照实输出，`|  |  |` 就是那行空表头。

**改法**：`fix_empty_table_header()` —— 空表头行 + 分隔行 + 有内容的正文行三者齐全时，
丢掉空表头、把首条正文行顶上去（顺手去掉它的 `**`，表头本来就加粗）。

## 50. 中文序号章标题**全部**掉成段落（一个锚点都没有）

**现象**：`从 RAGFlow 到 GraphRAG` 一篇的 `一、`/`二、`/`三、` 三条章标题
**全部**是普通段落，大纲里一条章都没有。

**根因**：`promote_cn_numbered_heads()` 原来的唯一闸门是「全文已有 **≥2 个**
中文序号**标题**」—— 拿已存在的标题当锚点。可这篇一个锚点都没有，闸门永远打不开。
（`#46` 修的是「有锚点、个别章掉队」，和这条不是一回事。）

**改法**：加「全掉模式」—— 没有锚点时可整组认，但闸门更严：

1. ≥3 个候选行；
2. 序号必须**从 `一` 起连续递增**（1、2、3…，缺一个就整组不动）；
3. 每行仍要过「短行 ≤ 40 字 + 不以 `。；，` 收尾」；
4. 层级直接给 `##`。

**为什么敢整组动**：正文里顺口写的「一、…」通常零散、不连续；而章号体系必然连续。
宁可漏，不接受误提。

**回归**：17 篇里只有本篇命中（其余文章没有中文序号体系）。单测覆盖
「不连续不补」「不足 3 个不补」「带句号的候选不补」。

## 51. 章用中文序号、节用 `1、2、`（顿号）⇒ 章与节同级

**现象**：同一篇里 `## 一、RAGFlow 引擎架构解读` 和 `## 1、召回精度瓶颈` **同为 `##`**，
大纲里「章」和「节」并列。

**根因**：`classify_head_number()` 把 `1、` 判成 `int`，硬编码层级 2。
它的口径来自「`1 容器平台网络模型` 是章」的那批文章 —— 那些文章**没有**中文序号章。

**改法**：`rebuild_headings()` 里记住最近一个中文序号章标题的层级 `cn_level`；
当层标题形如 `^\d{1,2}、`（**中文顿号**）时，层级改成 `cn_level + 1`。

- 顿号是「小节」的强信号，`1 ` / `1.` 不受影响（那是另一套口径）；
- 没有中文序号章体系时 `cn_level == 0`，`1、` 仍是 `##`（单测覆盖，防凭空降级）。

## 52. `（1）图构建引擎` 这类括号编号小节掉成段落

**现象**：`从 RAGFlow 到 GraphRAG` 里「（1）图构建引擎 /（2）图数据库与存储层 /
（3）图推理与检索层 /（4）语义融合与生成」，四条小节全是普通段落，大纲里整组消失。

**根因**：公众号不给 `（1）…` 标题样式，抓取器自然拿不到 `<hN>`；
而 `rebuild_headings()` 只认 `1` / `1.1` / `01` 三种编号，括号编号**从来不是**本项目的
标题编号（`BOLD_LIST_ITEM_RE` 还明确把加粗的 `（1）…` 当列表项）。

**改法**：新增 `promote_bracket_heads()`，闸门全中才动：

1. ≥3 个候选，编号**从 1 起连续递增**；
2. 每个候选是短行（≤ 40 字）、不含句号、不以句末标点收尾 ——
   「（1）全局推理能力：GraphRAG 能够…。」这种带正文的长句自动落选；
3. 同组统一挂到「前面最近的标题」下一级（**不要逐个累加**，否则会
   3 条候选变成 `###`/`####`/`#####` —— 第一版就是这么错的，回归立刻抓到）。

**回归**：17 篇里有 2 篇命中，**都是真小节**（「基于知识图谱增强 RAG」的
`（1）～（6）增强 RAG …`、「容器云平台网络架构」的 `（1）NodePort …`），
其余长句候选未被误提。这类「命中既有成品但确实是改进」的改动要逐条看过再放行。

## 53. 「构成式」加粗行被提成假章节

**现象**：`图解从 IP 到 SRv6` 里两次出现

```
**外层运输标签 + 内层 VPN 业务标签 + 原始 IP 数据包**
```

被提成 `## 外层运输标签 + …`，大纲里凭空多出一章。

**根因**：`bold_can_be_head()` 的判据只有「长度 ≤ 40 / 不含句号 / 不以句末标点收尾」，
这类「报文由哪几层拼成」的强调句全部满足。

**改法**：加一条 —— 含**带空格的加号**（`\s\+\s`）的加粗行一律不当标题。
必须带空格，`C++` / `A+B` 这类词不受影响（单测覆盖）。

## 54. 行尾标点被单独加粗：`…路径执行**。**`

**现象**：正文某行以 `路径执行**。**` 收尾，Obsidian 里那个句号是无谓的加粗。

**根因**：微信编辑器把句末标点单独包了一层 `<strong>`。

**改法**：`re.sub(r"\*\*([。，、；：？！,.;:!?])\*\*(?=[ \t]*$)", r"\1", …)`。

⚠️ **必须限定行尾**。第一版没加 `(?=[ \t]*$)`，于是行中的
`**…很远距离**。**L5 级…驱动**`（两段并列加粗）被并成一段，**强调范围直接变了** ——
全量回归里「79页RSI综述」一篇立刻报差异，才发现的。

## 55. 文末裸 `#标签` 行与 frontmatter 重复

**现象**：旧产物末尾有一行 `#主题/AI/RAG #类型/技术教程 #来源/微信公众号`，
而 frontmatter 里已经有同样的三层标签。库里的存量笔记则写着另一套**实体词**
（`#网络 #MPLS #SRv6 #路由`、`#Metrics #链路追踪`）—— 说明这一行原本承载的是细粒度实体标签，
后来被流水线当成了「frontmatter 的副本」，两种含义混在同一位置。

**根因**：同一份信息维护两处，且两处语义漂移。

**改法**（2026-11-04，用户决定）：**彻底不写**。标签只放 frontmatter。
改动影响全部 17 篇的产物，因此按 §5.1 做了全量回归：新旧脚本各跑一遍，
逐篇比对确认「差异只有这一行 + 尾部空行」，零误伤。

## 56. frontmatter 的 tags 有两种缩进，解析器只认一种

**现象**：`update_index.py --from-md`、`sync_to_vault.py`、`verify_wechat_md.py`
都读不到标签，报「tags 为空」，但文件里明明有。

**根因**：`yaml.dump()` 输出**无缩进**序列：

```yaml
tags:
- 主题/AI/RAG
```

而 Obsidian 的 Linter 类插件会重排成 **2 空格缩进**：

```yaml
tags:
  - 主题/AI/RAG
```

三处各写了一份 `^  - (.+)$` 或 `^- (.+)$` 的正则，于是「刚写完的文件能读、库里存量读不到」。

**改法**：收敛成一个 `tag_infer.parse_frontmatter_tags()`，三种形态都认
（无缩进 / 2 空格 / 行内 `tags: [a, b]`），三处调用方共用。
教训：**同一份数据不要有三个解析器**。

## 57. 体裁（类型标签）不能靠正文关键词加权

**现象**：第一版用「标题×6 + 大纲×3 + 正文×1」统一打分推断类型，28 篇样本只有
**64%** 命中。典型误判：`图解从IP到SRv6…？` 被判成「观点随笔」。

**根因**：正文里「如何 / 为什么 / 落地 / 模板 / 实践」出现频率极高，
加权后压过标题信号；标题里的问号也被当成了随笔特征。

**改法**：类型改成**按标题的优先级级联**（教授 → 模板 → 速查 → 个股 → 研报 →
趋势 → 实践 → 教程 → 随笔），正文只在一条标题规则都不中时兜底，且要求
「≥3 分且 ≥2.5 倍于第二名」，否则回落 `类型/技术教程`。命中率 64% → **86%**。

⚠️ 级联顺序本身是规则的一部分 —— `浅谈…能力建设实践` 同时含「浅谈」（随笔）与
「实践」（实践），必须实践在前，否则判错。调序等于改规则，改完要重跑准确率基线。

## 58. 落库目录会实时改名，写死路径必炸

**现象**：一次会话内，vault 连换三版 —— 先是 `<vault>\iNote`，再是 `<vault>\笔记库\公众号`，
又拍平成 `<vault>\公众号`，最后变成 `<vault>\【NN】公众号`（统一加编号前缀）。
写死路径的脚本三次全部落空（`FileNotFoundError` / 写到不存在的层级）。

**根因**：用户在重整知识库目录（统一加 `【NN】` 前缀），而脚本把目录名当常量。

**改法**：落库目录与索引文件名一律配**通配模式**（`WECHAT_SUBFOLDER_PATTERN=*公众号`、
`WECHAT_INDEX_PATTERN=*知识库索引*.md`，写在 `.env` 里），运行期 glob 唯一候选；
命中多个就**报错而不是猜**。（早期这两个值放在 `local_config.py`，2026-11-04 起迁到 `.env`。）

## 59. `python -c` 传中文路径给原生 Windows Python 会「文件不存在」

**现象**：同样的路径 `ls` 能列出内容，写成文件跑也能读到，但
`python -c "Path(r'C:\…\【15】公众号')"` 报
`FileNotFoundError: 系统找不到指定的路径`。

**根因**：Git Bash 按当前代码页把 `-c` 后面的命令行交给原生 Windows Python，
命令行里的 CJK 字节在这一跳被错误转码，Python 收到的路径字符串已经变形 ——
所以它报的「路径不存在」是**真的不存在**，只是那个路径不是你写的那个。
这条和 #58 症状一模一样（都是 `FileNotFoundError`），但一个是目录真变了、
一个是编码坏了，混起来会白查半小时。

**改法**：需要跑带中文路径的 Python 代码时**写成 `.py` 文件**再执行，别用 `-c`。
排查顺序：先用 `ls` 确认目录在 → 再怀疑编码，而不是先怀疑路径。

## 60. 索引重跑会把人工缩写与摘要冲掉

**现象**：`update_index.py` 对已存在的条目重跑一次，`[[长标题|短名]]` 里的短名
被换成标题全称，写好的「— 一句话价值点」也变成新的默认值。

**根因**：更新逻辑直接用「本次参数」重渲染整行，没给 `--display` / `--summary`
时就用默认值填空 —— 等于把人工成果覆盖成空白。

**改法**：更新已有条目时，**没显式传的参数沿用库里已有值**（从原行解析出
显示名与摘要）。索引是人工维护物，脚本只能补不能吞。

## 61. 段落末尾的 `---` 分隔线被当成段内内容

**现象**：往「安全」这种最后一段追加条目，结果写到了 `## 三、索引维护` 上面、
`---` 分隔线之下。

**根因**：`insert_pos` 只跳过空行，`---` 是非空行，于是被当作「段内最后一行」，条目插在它后面。

**改法**：把 `---` / `***` / `___` 这条水平线当**硬边界**，遇到就往回退一格再插。
单测 `test_flat_section_does_not_create_group` 锁住这个行为。

## 62. 配置写进 `.py` 也算泄漏，且 `.gitignore` 只对**未跟踪**文件有效

**现象**：`scripts/local_config.py` 里存着完整 vault 路径（含用户名）却「一直没事」，
因为它始终在 `.gitignore` 里。但换个仓库、换台机器、或者某次 `git add -f`、打包、
备份工具扫全目录时，它就跟着走了。

**根因**：两条独立的风险叠在一起：
1. 只要它是**代码**（`.py`），就有被当源码处理的路径（打包、`pip install .`、IDE 索引）；
2. `gitignore` 对**已经被跟踪**的文件完全无效 —— 历史上 add 过一次，之后加规则也不会让它消失。

**改法**：私有值迁到仓库根 `.env`（纯配置，惯例明确），公开模板 `.env.example` 只放占位符；
`.gitignore` 写 `.env` + `.env.*` 再 `!.env.example` 白名单，防止 `.env.local` / `.env.bak` 漏网。
审计时别只看当前树，要查历史：`git log --all -p` 里搜用户名与本机目录特征串。

## 63. `.env` 被写成带 BOM，于是只有第一项失效

**现象**：`.env` 第一行明明写着 vault 路径，脚本却说「未配置」；后面的键一切正常。

**根因**：Windows 记事本与 PowerShell 5 的 `Out-File` / `>` 默认写 **UTF-8 带 BOM**。
BOM 粘在第一行键名前面，键名成了 `\ufeffWECHAT_VAULT`，正则匹配不上 ——
于是只有第一项悄悄失效，肉眼完全看不出来。

**改法**：`parse_env_text()` 开头先剥 `\ufeff`；`load_env()` 用 `utf-8-sig` 读。
单测 `test_strips_bom` 锁住。同类坑在 CSV / JSON 也有：见到「只有第一行不对」先怀疑 BOM。

## 64. 删掉的东西会「复活」：`output/` 里的旧产物才是落库的真实来源

**现象**：2026-11-04 把 vault 里 28 篇笔记末尾那行裸实体标签（`#MPLS #SRv6 #路由`）
统一清掉了，`to_obsidian.py` 也不再生成它。但只要对**同一篇文章**重跑一次落库，
那行标签又回来了。

**根因**：落库读的是 `output/<目录>/<目录>.obsidian.md`，那是**当时**的转换产物。
清 vault 只清了终点，没清中间产物 —— 17 个旧 `.obsidian.md` 里全都还带着那一行。
顺着这个逻辑，任何「改了转换规则 + 只重跑落库」都会得到旧结果，而且看起来像是规则没生效。

**改法**：两件事一起做才干净 ——
1. 一次性迁移脚本清存量（判据：该行**后接 `## 相关笔记`** 或**位于文件末尾**，且整行只由
   `#词` 组成；正文中间的同类行一律不动 —— 28 篇里有一半的标签行在 `## 相关笔记` **之前**，
   只认「最后一行」会漏掉 27 篇）；
2. `sync_to_vault.strip_tail_tags()` 在落库时再删一次，幂等兜底。
**通用教训**：改的是「转换规则」时，一定要重跑**转换**；只重跑下游，拿到的还是旧东西。

## 65. 索引里的「覆盖计数」只要靠人工追，就一定会滞后

**现象**：索引页「一、标签体系」写着 `宏观 8`、`类型/模板 2`，实测只有 7 篇和 1 篇。
不是算错，是当初填完就没人再动过 —— 中间的改标签、移目录、删笔记都没同步。

**改法**：新增 `scripts/tag_stats.py`，从全库 frontmatter 重算，并接进
`update_index.py`（落库登记后自动跑一次）。约束是刻意的：

1. **只改数字与条目**。标签名、行顺序、判定标准、说明文字一律原样保留 ——
   覆盖数是「事实」可以算，判定标准是「判断」只能人写。
2. **0 篇不列**。数到 0 的二级项默认移除（索引只该列真实存在的标签），
   要保留定义加 `--keep-zero`。留着 `RAG 0` 只会让人以为「有这么个标签」。
3. **三种显示写法都要认**。短名 `智能体`（→ `主题/AI/智能体`）、
   半截路径 `` `行业/银行` ``（→ `主题/行业/银行`）、完整路径 `主题/AI/RAG`。
   只认一种就会把 10 篇算成 0 —— 这个错第一次跑就踩到了。
4. **不猜**。表里的写法若命中多个同名标签，抛 `AmbiguousTag`、退出码 2，
   要求写成完整路径。静默取 0 是最坏的结果：数字「看着刚更新过」，其实是错的。

**另一个坑**：重排表格要用**显示宽度**（CJK 与全角符号按 2 计，`unicodedata.east_asian_width`
的 `W`/`F`），按字符数 pad 会让中文列全部错位。单测 `test_display_width_pads_cjk` 锁住。

**还有一个**：同篇数的并列项要用**稳定排序**（只按篇数排，不加名字做次级键），
否则 `负载均衡 3 · SDN 3` 会被按字符序重排成 `SDN 3 · 负载均衡 3` —— 数字没变，
但每次跑都动一次表格，diff 里全是噪音。

## 66. 以点开头的目录也会被当成笔记计入「全库 N 篇」

**现象**：全库篇数算出 71，实际只有 70 —— 多出来的是一篇
`.claudian/opencode/metadata/system.md`（某个工具自己写的元数据）。

**根因**：只排除了 `.obsidian` / `.trash` 这两个**点名**的目录，其它点目录照单全收。

**改法**：`tag_stats.collect()` 里凡路径段以 `.` 开头一律跳过。
同类风险在 `sync_to_vault` 与 `verify` 的遍历里也存在：新增遍历时别只想着 `.obsidian`。

## 67. 「其他」行把一级标签藏成半截路径，索引看着完整、实际漏算

**现象**：主题表最后一行是

```text
| 其他 | `行业/银行` 10 · `架构/高可用` 2 · `管理` 2 · `软技能/汇报表达` 2 |
```

数字全对，但这 4 个一级标签（`主题/行业`、`主题/架构`、`主题/管理`、`主题/软技能`）
在表里**没有自己的行**。只要 `主题/行业` 下再多一个二级（如 `主题/行业/证券`），
这一格就无处安放；更糟的是脚本当时只维护「已有行」，新出现的一级永远不会被补进来 ——
那部分笔记在所有数字里都消失了，而索引表面一点异常都没有。

**根因**：把「一级标签」和「兜底杂项」混成了同一个概念。兜底行的结构是自由的，
自由结构 = 无法被程序维护 = 迟早失真。

**改法**：
1. 每个一级标签都要有独立行，「其他」这种混装写法删掉；
2. `_update_theme_table()` 末尾检查「库里有一级、表里没这行」→ 补整行，
   二级按篇数降序生成，并打印 `已追加整行（N 篇）`；
3. 一级被笔记直接使用（如 `主题/管理` 2 篇、无二级）时写
   `一级直挂（N 篇）——暂无二级`，脚本只改括号里的数；
4. 该一级在库里彻底消失 → 整行删除，不留 `（0 篇）`。

**通用教训**：凡是要被程序持续维护的表格，**每一行都必须是同一套结构**。
为了让「暂时不好归类」的东西有个去处而设计的兜底行，最后一定会变成漏算的黑洞。
